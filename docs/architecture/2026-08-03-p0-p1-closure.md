# Core / TUI / CLI P0/P1 生产化闭环

日期：2026-08-03

## 结论与适用范围

本轮已经闭合代码仓库内可落地的 P0/P1 问题，覆盖 Core、SessionManager、TUI/CLI、
IPC/HTTP daemon、网络代理、会话数据、容器/Kubernetes 执行和发布门禁。这里的“闭合”表示
安全不变量已进入实现并有回归测试；它不等于某个组织的生产发布已经获批。真实 PostgreSQL、
对象存储、CNI、KMS/Vault、签名证书、模型质量基线、灾备演练和 30 天 canary 仍须在目标环境验收。

新的生产入口必须同时启用 Workspace Trust、`workspaceScope`、鉴权传输和受控运行时。Core 为旧嵌入方
保留的兼容缺省不是推荐的生产配置。

## Workspace Trust 与 restricted mode

### 操作命令

```bash
# 查看当前真实路径、信任状态、原因和执行来源；只读，可输出 JSON
anicode trust status --cwd "$PWD"
anicode trust status --cwd "$PWD" --json

# 必须在真实交互终端中逐字输入 canonical workspace path
anicode trust grant --cwd "$PWD"

# 立即撤销；下一次 open/send 会重新评估
anicode trust revoke --cwd "$PWD"
```

`trust grant` 不接受 `--json`、管道输入或非 TTY 自动化。确认期间如果工作区 identity 或执行面指纹发生
变化，grant 会拒绝，用户必须重新审查。trust store 的目录/文件权限为 `0700`/`0600`，并使用带
PID+随机 token 的跨进程锁、原子 rename 与 fsync；活进程持有的旧锁不能仅因时间到期被抢占。

未信任或检查失败时，入口仍可打开工作区，但只进入 restricted mode：

- 对 `not-trusted`、`execution-config-changed` 等可验证的未信任状态，交互式普通入口使用 `default`
  逐项授权，而非固定为 `plan`。受控 registry 保留内置 `read`、`glob`、`grep`、`write`、`edit`、
  `apply_patch`、`bash`、`todo_write`，以及 `bash_output`、`write_stdin`、`list_shells`、`kill_shell`
  等 shell 生命周期工具；写入、命令和 shell stdin 必须逐项确认，受限 `bash` 固定使用
  workspace-write sandbox 且没有联网参数；
- `inspection-failed` 无法证明安全边界，即使请求 `default` 也严格退回 plan 模式下的
  `read`、`glob`、`grep`，不提供写入或 shell；
- 禁用会话级 PatchSet、持久化授权、permission profile、MCP、LSP、browser、web search、hooks、
  subagent、skills、project memory、repo map、checkpoint、workspace network proxy 与自定义工具；
- 显式 `--auto` / `--accept-edits` 退回严格只读工具面，运行时 mode/profile 切换也不能扩大
  restricted policy；无头 CLI 与无交互 MCP 入口无法完成逐项确认时 fail closed；
- 项目 `.env*` 不加载，项目执行配置与项目插件/agents/skills/commands 不发现；
- TUI 以 `SessionSnapshot.workspaceTrust` 为 authoritative 状态，opening/reconnect 阶段先按未信任处理，
  不沿用上一个会话的 UI 状态；
- trust resolver 抛错、返回无效结构或执行面在 send 前改变，都按未信任处理。

Workspace Trust 不是 shell sandbox。授信只启用经审查的项目能力，不代表自动批准内置工具，也不放宽
权限引擎、网络、凭据、runtime 或 workspace scope。restricted mode 中的内置 `apply_patch` 是逐项授权的
文件工具，不等同于会话级 PatchSet prepare/apply/recovery 工作流。

## HTTP daemon 的安全启动

推荐的本机启动与连接方式：

```bash
# 默认监听 127.0.0.1:8327，启动成功后打印 token file 路径，但不打印 token
anicode serve --cwd "$PWD"

# 本机默认端口可自动推导 token file；显式写出更适合服务管理器
anicode --http http://127.0.0.1:8327 \
  --http-token-file /private/runtime/path/anicode.sock.http-8327.token
```

运维约束如下：

- 默认端口是 `8327`；`8317` 是内置 CLI Proxy/OpenAI-compatible provider 的端口，二者不再冲突；
- `serve` 先成功 bind，再原子发布 token file，避免 `EADDRINUSE` 时提前轮换仍在运行的服务凭证；
- token 至少由 32 个随机字节生成，token 目录/文件必须为当前用户拥有且分别是 `0700`/`0600`，
  symlink、超大文件、宽权限或错误 owner 都 fail closed；
- Unix socket 自定义父目录也必须是当前 uid 拥有的真实目录且精确为 `0700`；生产 server 无 token
  不能构造，唯一无鉴权入口是显式 test-only escape hatch；
- 除 `/healthz` 和 `/global/health` 外，REST、SSE 和模型发现都需要 Bearer；比较使用恒定时间函数；
- 客户端优先使用 `--http-token-file` 或 `ANICODE_HTTP_TOKEN_FILE`。兼容用
  `--http-token`/`ANICODE_HTTP_TOKEN` 仍存在，但可能暴露在 shell history 或进程参数中；
- server 只接受 `127.0.0.1`、`localhost` 或 `::1`。远端访问应由同机 HTTPS/mTLS 反向代理终止 TLS，
  同时保留 bearer、限流、请求体/SSE 上限和租户路由策略。

## Workspace scope

`workspaceScope` 是数据租户边界，不是展示层筛选。它在构造 manager 时 canonicalize 一次，并在每次
create、list、cold load、open/resume/send 和 fork 时重验目标 cwd。实现只接受与 scope 完全相同的
canonical workspace；不会因为字符串前缀相同而把 sibling 或子目录当成同一租户。

对域外会话：

- `listSessions` 静默过滤，避免泄漏 title/model/cwd；
- 已知 session ID 的 open/resume/send/fork 也返回统一 scope error；
- cold load 先检查 metadata header，正文读取后再复核，防止 list/load 之间被替换；
- legacy JSONL 迁移的 `list()` 只读取 metadata，只有该 session 通过上述 scope 预检后才读取并导入正文；
  同 ID 但 workspace identity 不同的 legacy 记录不会覆盖 primary；
- provider 构造、PatchSet recovery、runtime event 和 transcript 写入都发生在 scope 校验之后。

需要服务多个项目时，应为每个 canonical workspace 创建独立 manager/进程或由可信路由层创建独立实例，
不能取消 scope 后依赖 TUI 选择器隔离。

## `/model` 的实时发现语义

每次打开 `/model` 都刷新当前宿主可见的 provider 目录。远程 CLI 不在客户端读取本机 env 或访问模型
端点，而是通过已鉴权的 daemon IPC/HTTP 请求由服务端探测，因此结果与真正执行模型的进程一致。

当前约束：

- 每个 OpenAI-compatible provider 使用鉴权 `GET /models`，不发送 completion；debug provider 返回其
  本地目录；当前 adapter 不支持的 embedding、rerank、image、audio、realtime 等专用模型会过滤；
- provider 单次发现默认 2 秒、响应体最多 1 MiB、最多保留 500 个安全 model ID；TUI 默认并发 4，
  整轮最多 8 秒；
- 只有本轮成功响应的 provider/model 会展示；成功但空列表意味着没有可选模型，超时、401、429、5xx
  或网络错误在本轮 fail closed 为隐藏；
- 新一轮探测或会话切换会使旧代次结果失效，慢响应不能覆盖新结果；鼠标/Enter 选择、
  `/model <provider/model>` 和 `once` 在使用前再次查询 authoritative host；
- 探测结果是瞬时视图，不写回并删除内置 catalog。瞬时 429/5xx 只影响本次选择器；
  `--list-models` 仍是离线内置目录，不代表在线可调用。

这种设计比逐模型 completion ping 更合理：不会为打开选择器产生推理费用、消耗 token/配额或触发批量
限流，也能及时发现服务端新增/删除模型。它证明的是“宿主当前列出该模型”，不是对下一次推理成功的
保证；模型仍可能在选择后因并发配额、区域策略或服务故障失败，正常调用链必须保留错误处理和 fallback。

## 会话删除、保留与备份

显式删除是内容清除操作，`SqliteRuntimeDatabase.prune()` 是时间保留操作，两者不能混用：

- `deleteSession` 通过共享 SQLite/PostgreSQL lifecycle row 原子进入 `deleting`，拒绝新的 producer lease，
  中断并等待 live drive、cold load、command recovery 和已登记持久化操作，然后清除 command inbox、
  outbox、artifacts、runtime event/snapshot 与 transcript；这里的保证来自原子存储 transition，不应表述为
  “第一个 await 前”的进程内布尔值；
- lifecycle 同时持久化 canonical workspace 与 device/inode；目录被替换时 PatchSet 清理 fail closed，不能
  根据复用的字符串路径触碰新目录；`applying` journal 会在同一 workspace/session lock 内先做校验回滚并
  terminalize，真正的哈希冲突才让删除保持可重试；
- 删除后只保留 `session.deleted` 空 tombstone，供同步客户端观察删除，不含 prompt/response；
- 新写入的 File/S3 artifact payload 按 session 隔离。S3 在 session 前缀外先写永久、空内容删除标记；
  marker 立即让读取/再写 fail closed，版本化与非版本化前缀均按最多 1000 项批量清理；
- S3 可能在 producer 崩溃后才确认旧 Put，因此物理清除采用 retained marker + 周期/重启 reconciler 的
  持久收敛，而不是不可能证明的瞬时零残留。生产默认 60 秒，并必须有独立 maintenance run、失败告警、
  erasure SLO 与 Object Lock/MFA-delete 演练；
- 旧版全局 content-addressed blob 可能被多个 session 引用，因此只保留只读兼容，单会话删除不会移除。
  运维方应做引用审计/离线迁移后再按对象存储生命周期回收，不能由一个会话直接删共享 blob；
- `prune()` 默认只清理过期 audit、artifact 索引、terminal/job/event/outbox 事实，不自动删除用户会话或消息。
  用户内容必须经显式删除或组织定义、验证过的独立生命周期流程处理。

备份 SQLite 时必须使用 online backup 或同时一致快照 DB、`-wal` 和 `-shm`。PostgreSQL/S3 需要匹配的
生命周期、跨存储删除检查和定期 restore drill；“数据库行已删”不能当作对象 payload 已删的证据。

## 容器、Kubernetes 与写入事务

### Container backend

- image 默认必须使用 `@sha256:` 固定；root filesystem 只读，drop ALL capabilities，禁止提权，限制
  PID/CPU/memory，`/tmp` 使用 noexec/nosuid/nodev tmpfs，并以调用用户 UID/GID 运行；
- 无网络任务使用 `--network none`；有网络任务必须同时配置 Docker/Podman internal network 和受控出口
  proxy；凭据仅通过 Credential Broker 短租约注入并在输出中脱敏；
- `.git` 与 `.anicode` 即使在 workspace-write 也额外只读；timeout、AbortSignal、Docker CLI 错误等所有
  退出路径都等待 `rm --force`；
- 生产 remote/local stack 用 `TransactionalExecutionRuntime` 包裹 container backend：写命令在临时副本
  运行，失败/超时丢弃；成功时检查 source 未并发改变，再通过带锁与 fencing 的 PatchSet 原子提交。

### Kubernetes backend

- runner 使用 digest-pinned image、non-root、RuntimeDefault seccomp、read-only rootfs、drop ALL、
  `automountServiceAccountToken: false`、resources/active deadline/TTL；
- PVC/source mount 始终只读；ephemeral 模式只把 source 复制到受大小限制的 `emptyDir`，不会把 runner 的
  临时写入自动同步回 PVC；
- NetworkPolicy 默认拒绝，联网 Job 只允许到认证出口 proxy；上线前必须在目标 CNI 运行
  `deploy/remote-runtime/verify-isolation.sh` 覆盖 IPv4/IPv6、DNS、metadata、私网和无鉴权代理绕过；
- 当前实现对 Kubernetes `workspace-write` 明确 fail closed。只有在可信 control-plane PatchSet committer
  能验证 base hash、审批、fencing token 并原子提交时，才可重新开放；不得改成 runner 直接挂载可写 PVC。

## 发布门禁与验证证据

必须在仓库声明的 Node `>=22.15.0 <25` 和 npm `>=11.5.1 <12` 上运行：

```bash
npm ci
npm run verify:release
```

门禁按顺序执行：

1. `format:check`、`lint --max-warnings 0`、全 workspace `typecheck`；
2. SDK/OpenAPI `codegen:check` 与全量测试（含 Workspace Trust、scope、daemon、SSE、model discovery、
   deletion fence、proxy、container/Kubernetes、PatchSet/worker；PostgreSQL integration 在配置测试数据库时

3. production dependency high audit、build dependency policy audit、registry signature audit；
4. clean-room CLI package build/PTY smoke、Electron App build、VS Code extension build和 bundle size budget。

发布批准还必须附带目标环境证据：Linux/macOS/Windows required CI、真实模型 eval 基线与非回归、macOS

## 回归时必须守住的边界

后续新增项目级自动加载目录、可执行配置字段、daemon route、模型协议、artifact backend 或 remote write
path 时，至少同步完成以下工作：
